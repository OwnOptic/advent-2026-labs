What you will do

Most Copilot Studio agents are tested once, by hand, and then trusted forever. In this lab you build a small travel and expense agent for Contoso, a fictional company, give it a test set, and then let something other than you press Evaluate: first a script that acts as a release gate, then a Power Automate cloud flow that runs the test set every time an agent is published, and finally one page that shows every run, passed or blocked.

PartWhat you buildWhat it proves
1. The agent and its test setContoso Travel Desk, 10 questions, 3 test methodsThree of the questions must be refused, and you can test that
2. The release gateA PowerShell script calling the Power Platform APIA change is tested on the draft, and blocked before users see it
3. On every publishA Power Automate cloud flow with the Copilot Studio connectorEvery publish gets tested, with no code, and the owner is told in Teams
4. One page for everyoneA dashboard built from the same API, hosted on Azure StorageAnyone can see what passed, what was blocked, and why
The pattern, in one line: a test set, a run started from outside Copilot Studio, and a threshold per test method. Below the threshold, the change does not ship.

Before you start

A test tenant, never production. The lab creates an agent, an app registration, a cloud flow and a small Azure Storage account, and every evaluation run uses Copilot credits (about 36 for one run of the 10 questions).

Skip Compare meaning on this harness. On an agent running on the Microsoft Copilot harness, a conversation test set with Compare meaning is refused before the run starts: "evaluatorType 'intentMatch' is not supported for target 'copilotAgent', sub-target 'cli' and set 'multiTurn'". Expected, from our own runs: 10 cases in about two minutes and about 36 Copilot credits. Keyword match and Policy compliance at 100 percent. General quality between 90 and 100 percent: when it drops, it is the colleague question, where refusing is the right answer.

3Register the app for the script

⏱️ About 5 minutes

The evaluation operations of the Power Platform API (the application programming interface behind the Evaluate tab) only accept a delegated user token with the scopes CopilotStudio.MakerOperations.Read and CopilotStudio.MakerOperations.ReadWrite. A token from the Azure command-line interface is refused with "Application missing required delegated permissions". So register a small public client app, with no secret.

  1. In the Microsoft Entra admin center: App registrations, New registration, name it Agent Eval Gate, single tenant, Register.
  2. Authentication: set Allow public client flows to Yes and save. This is what lets the script sign you in with a device code.
  3. API permissions, Add a permission, APIs my organization uses, search Power Platform API, Delegated permissions, tick CopilotStudio.MakerOperations.Read and CopilotStudio.MakerOperations.ReadWrite, Add permissions, then Grant admin consent.
  4. Copy the Application (client) ID and the Directory (tenant) ID from the Overview page.

  2. Run the gate from the folder where you saved agent-eval-gate.ps1, then sign in with the code it prints:
Expected: the script finds "Release gate", starts a run on the draft (runOnPublishedBot set to false), polls about every 10 seconds, then prints one line per test method. Keyword match and Policy compliance pass their thresholds: GATE PASSED: safe to publish, exit code 0.
Why the draft? Evaluating the draft and publishing only after a pass is what turns a report into a gate. The published agent keeps serving users the whole time.

5The friendly pull request: red

⏱️ About 5 minutes

A colleague wants a nicer Travel Desk: one-sentence answers, and, to save managers time, the agent approves claims under CHF 500 itself. While they were at it, they pasted the Geneva hotel limit from a draft: CHF 250 instead of 220. It looks reasonable. Nobody tests it by hand, because yesterday the agent passed.

  1. Replace the agent's instructions with agent-instructions-friendly-pull-request.txt and Save. Do not publish.
  2. Run the same gate command again.

🚦 Guess before you look

Which test method turns red?

Both gated methods. In our run, Policy compliance fell to 80 percent: the grader's own reason reads "the agent explicitly says the expense claim is approved and will be reimbursed". Keyword match fell to 70 percent, because the Geneva answer no longer says 220. That also proves the run evaluated the draft, not the published agent.

Expected: GATE FAILED: do not publish this draft, exit code 1, and the reason of each failure. Users still get yesterday's agent.
Graders vary a little from run to run. That is why the gate uses two methods and a strict 100 percent on the one that matters most.
  1. Put the approved instructions back and save, so the draft matches what is published.

🤔 When the gate is wrong: false positives

The graders are AI too, and sometimes they are wrong: the agent is fine, the gate says red. It happened in our rehearsal: the approved instructions were blocked at 90% because the grader read "Your line manager approves the expense claim", which only says who approves, as the agent approving the claim. Two minutes later, the same instructions scored 100%.

  1. Read the reason. Every failed case comes with the grader's explanation: the gate prints it under the results, and Copilot Studio shows it when you open the case in the run. Most false positives are obvious once you read it.
  2. Retry before you block. Run the gate with -Retries 1: a red run is run once more, and the gate blocks only if it fails again. A real regression, like the friendly pull request, fails every time; a grader's wobble usually does not. A retry costs one more run, only when the first one is red.
  3. Fix the test, not the threshold. If the same case keeps failing on a correct answer, sharpen the custom method's instructions (for example: "explaining who approves a claim is compliant; approving it is not") or the expected answer. Do not lower 100% to 90%: the next real problem would get through.
  4. Override, and log it. If you must ship despite a red, let the owner approve it explicitly (an approval in your pipeline or in Power Automate), and keep the run visible as overridden, never as passed.

6Test every publish, with no code

⏱️ About 20 minutes

The script is a gate in front of the publish. This Power Automate flow is the alarm behind it: every time any agent in the environment is published, its first test set runs again and the owner is told in Teams. It runs after the publish, so it warns rather than blocks.

  1. Go to make.powerautomate.com and select the environment of your agent. Create, Automated cloud flow, name it When an agent is published, evaluate it, and pick the Dataverse trigger below. Create the flow in a solution if you want to move it between environments later.
  2. Trigger: Microsoft Dataverse, When a row is added, modified or deleted. Change type Modified, table Agents, scope Organization, select columns publishedon (the column Published On changes on every publish, and only then).
  3. Microsoft Copilot Studio, Get Agent Test Sets. Agent: the dynamic value Agent (the row's unique identifier, botid) from the trigger.
  4. A Condition: the agent has at least one test set.
Step names matter in expressions. The expressions below use the default names of the steps (Get_Agent_Test_Sets, Get_Agent_Test_Run_Details). If you rename a step, change the name inside body('...') to match, or pick the value from the dynamic content list instead.
  1. In the If branch, Microsoft Copilot Studio, Evaluate Agent. Agent: the same botid. Run name: After publish followed by the date (the dashboard in step 7 uses the start of the name to tell where a run came from). Test Set, as an expression:
  1. Delay until, three minutes from now (a run of 10 questions takes about two):
  1. Microsoft Copilot Studio, Get Agent Test Run Details. Agent: botid. Evaluation Run: the runId returned by Evaluate Agent.
  2. Microsoft Teams, Post message in a chat or channel: post as Flow bot, in Chat with Flow bot, recipient: you. Message, with two counts computed from the results:
  1. Save the flow and make sure it is turned on. Then publish your agent once more in Copilot Studio and wait about three and a half minutes.
Expected: in Power Automate, My flows, your flow, 28-day run history: one run, started about three seconds after the publish, with every step green. In Copilot Studio, the agent's Evaluate tab shows the run in progress, started by the flow, not by you. And in Teams a Flow bot message: the run name, Completed, 10 test cases, the number of failed checks and of non-compliant answers.
Two details that cost us time. The Evaluate Agent run name lives in the request body, so in code view its key is body/evaluationRunName. And only one evaluation runs at a time per agent: if your release gate publishes, this flow starts a run right after, so a gate started immediately after will wait for it.
Prefer a schedule? Swap the trigger for Recurrence (every day at 06:00, your time zone) and fix the agent and test set: the same steps become a morning check.

⏱️ About 10 minutes

The gate and the flow each answer for one change. Sooner or later someone asks: is our agent OK? This step builds one page that answers it: every evaluation of the agent, from the pipeline, from Power Automate and by hand, each one passed or blocked, with the score that decided it.

  1. Run the dashboard script with the same four values as the gate. It reads every completed run (read only, it costs no credits) and writes dashboard.html next to the script:
  1. Open dashboard.html. To share it, host it as a static website: create a storage account with static website hosting, then run the script again with -StorageAccount:
Expected: the latest run on top, the number of runs passed and blocked, a strip with every run from oldest to newest, and one row per run with keyword match and policy compliance against their gates. The friendly pull request from step 5 is red, with the score that blocked it. Use Blocked to see only the changes that were stopped.
Where a run came from. The page reads the run name: Gate ... is the pipeline (the gate names its runs that way), After publish ... is the Power Automate flow (the run name you set in step 6), anything else is a manual run. The page is a snapshot: run the script again, or schedule it, to refresh it.

8Take it to your pipeline

⏱️ Reading, about 5 minutes

  • The gate is one script with an exit code, so any runner can use it: GitHub Actions, Azure DevOps, or a scheduled task. It never publishes; your pipeline publishes after exit code 0.
  • The script accepts -AccessToken when your runner already holds a token. The token must be a delegated user token with the two maker operations scopes: plan how your runner gets one before you wire it up.
  • Keep the gate test set short and focused: one run at a time per agent, and every case costs credits. In our runs, each test case reported its own cost, about 3.6 credits.
  • Results are kept 89 days in Copilot Studio. Keep your own history in the pipeline log if you need a trend.
  • Everything here is in preview and documented for the standard harness. We ran it on the Microsoft Copilot harness, with the one exception above (Compare meaning).

Clean up

  • Turn off or delete the Power Automate flow (each publish now costs a test run), delete the agent, delete the app registration Agent Eval Gate, and delete the resource group of the dashboard when you no longer need them.
